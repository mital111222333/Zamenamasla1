## Найденные уязвимости

### 1. Захват платформенной админки через «чек» в формате SVG — **критично, исправлено**

Любая точка (регистрация открыта всем) могла загрузить как «чек об оплате» SVG-файл
со скриптом: проверка пропускала любой тип `image/*`, который присылает браузер.
Когда администратор открывал чек в админке, файл показывался с нашего сайта как
`image/svg+xml`, и скрипт выполнялся **от имени администратора** — мог создать точки,
сбросить пароли, скачать базу.

Исправление (`subscription.py`):
- тип файла определяется по первым байтам содержимого (JPEG, PNG, WEBP, GIF, HEIC, PDF), а не по имени;
- SVG/HTML/всё остальное отклоняется и пишется в журнал;
- при просмотре чека картинки отдаются с `Content-Security-Policy: sandbox`, всё неизвестное — только скачиванием.
  Это защищает и от чеков, которые уже лежат в базе.

### 2. Уязвимые версии библиотек — **высокий, исправлено**

`pip-audit` нашёл 16 известных уязвимостей в `flask 3.0.3`, `cryptography 43.0.3`,
`requests 2.32.3`. Обновлено в `requirements.txt`, все тесты проходят.

### 3. Нет лимитов частоты на публичных адресах — **средний, исправлено**

Адреса табло, камеры, паспорта машины, регистрации и платёжного callback можно было
дёргать без ограничений (перебор токенов, нагрузка на единственный процесс с сайтом
и ботом). Теперь лимиты в `security.py → RATE_RULES`, превышение → ответ 429 и запись в журнал.

### 4. Слабые пароли — **средний, исправлено**

Минимум был 6 символов, принимались `123456`, `12345678`. Теперь ≥ 8 символов,
без частых паролей и без совпадения с логином (регистрация, сотрудники, сброс пароля).
Уже существующие пароли продолжают работать.

### 5. Мало следов подозрительной активности — **средний, исправлено**

Новый журнал `security_events` (хранится 90 дней). Записываются: неверные пароли,
блокировка входа, входы в админку, неверные коды сброса, подбор кода, запросы с чужих
сайтов, превышение лимитов, отклонённые файлы, поддельные уведомления об оплате.
Срочные (`high`) события сразу приходят в Telegram на `ADMIN_TELEGRAM_ID`
(одно и то же — не чаще раза в час). Посмотреть журнал: войти в `/admin` и открыть
`/api/admin/security_events` (фильтр: `?severity=high`).

### 6. Сессия админки жила до 31 дня — **низкий, исправлено**

Теперь 12 часов; после этого нужно войти заново. У точек всё как раньше.

## Что проверено и в порядке (исправлять не пришлось)

- SQL-инъекции: все запросы с параметрами `?`; динамические имена колонок берутся только из кода.
- Изоляция точек: каждый запрос берёт `shop_id` из сессии; доступ к филиалам проверяется `is_branch_of`.
- XSS в шаблонах: `|safe` используется только для своих статичных текстов.
- CSRF: проверка `Origin/Referer` для всех изменяющих запросов.
- Восстановление базы: только админ, фраза-подтверждение, защита от «zip-бомбы».
- Подпись Hamyon: `compare_digest`, сумма берётся из нашей записи, а не из запроса.
- Без входа ни один закрытый адрес не отдаёт данные (проверено тестом по всем 230+ адресам).
